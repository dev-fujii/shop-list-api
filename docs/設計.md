# 設計

2026-10-17 時点。作りながら調整する。2026-11-04 にアカウント作成とログイン、取引の登録の冪等キーの内容を足した。要件は `docs/要件定義.md`。

## API の一覧

- 1回のリクエストで1つの操作をする（REST）。まとめて送る API（バッチ API）は作らない。
- どの API も、ログインした人のデータだけを扱う。
- 呼ぶ人を確かめる入口は2つ。
  - ログインのトークン: `Authorization: Bearer （トークン）`。アカウント作成とログイン以外の、すべての API で使える。
  - 決まった鍵: `X-Api-Key: （鍵）`。iPhone のショートカットのように、人が操作しない入口のためのもの。設定に書いた1人のユーザーとして扱う。呼べるのは取引の登録（`POST /transactions`）だけで、それ以外を鍵で呼ぶと 403。鍵が漏れても、他人ができることを取引を足すことだけにするため。
- 何も付けていない API は、すべてトークンか鍵が必要（`FallbackPolicy`）。付け忘れても閉じたままになるので、開けるところ（アカウント作成とログイン）にだけ `[AllowAnonymous]` を付ける。
- 送るもの・返すものの中身は、別の節で決める。
- URL の先頭に `api/` は付けない。API だけを返すサーバーで、画面などと分ける必要がないため。あとから付けると、iPhone のショートカットに書いた URL も直す必要があるので、変えない。

| PUT | `/category-rules/{id}` | 分類ルールを直す | 204 | 400（入力）、404 `category_rule.not_found`、409 `category_rule.duplicate_keyword`、422 `category.not_found`（存在しない分類を指定） |

### 集計

| メソッド | URL | やること | 成功 | 主なエラー |
| --- | --- | --- | --- | --- |
| GET | `/summaries?month=2026-10` または `/summaries?from=2026-10-01&to=2026-10-31` | 月か期間の集計を取る（分類別の合計、支出の合計、収入の合計、収入 − 支出の残り）。条件は `month` か、`from` と `to` のどちらか一方で渡す。条件がなければ、今月を含めた3か月 | 200 | 400（条件が正しくない。`month` と `from`・`to` を両方送った、存在しない日付、`from` が `to` より後など） |

- 集計は1つのリソース（`/summaries`）として扱い、月か期間かは絞り込みの条件の違いにする（取引の一覧と同じ形）。
- 条件を何も送られなかったときは、日本時間の今月を含めた3か月（今日が 2026-10-17 なら 2026-08-01 〜 2026-10-31）の集計を返す。「3か月」は設定ファイル（`appsettings.json`）に置く。

### アカウントとログイン

| メソッド | URL | やること | 成功 | 主なエラー |
| --- | --- | --- | --- | --- |
| POST | `/accounts` | アカウントを作る。その人の初期分類（6個）も一緒に作る。トークンも鍵も要らない | 201 | 400（入力）、409 `account.duplicate_user_name`、429（回数の超過） |
| POST | `/tokens` | ログインして、アクセストークンを受け取る。トークンも鍵も要らない | 200 | 400（入力が無い）、401 `token.invalid_credentials`、429（回数の超過） |

- ログインは「トークンを作る」操作として、`/tokens` への `POST` にする。
- パスワードの再設定・ログアウト・更新トークンは作らない。再設定はメールを送る仕組みが無いため。トークンの期限を60分と短くし、更新トークンを作らないので、ログアウトは呼ぶ側がトークンを捨てることで代わりにする。
- アカウントを消す API は、今は作らない。

### ページ分割

- 件数が増え続ける一覧（取引、分類ルール）は、何件かずつに分けて返す。分類（10〜20個）と集計（1件）は分けない。
- URL の例: `GET /transactions?page=2&pageSize=50`
- 何も指定されなかったときは1ページ 50件、指定できる上限は 100件。上限を超えた `pageSize` は 400 で断る（100 に直して返すことはしない。呼ぶ側が間違いに気づけるように）。`page` と `pageSize` が 0 以下も 400。最後のページより後ろの `page` は、エラーにせず空の `items` を返す。
- この値は設定ファイル（`appsettings.json`）に置き、オプション パターンで読む。運用しながら調整したい値なので、ビルドし直さずに変えられるようにする。入力チェックの値は DB の形に関わるので、設定ファイルではなくコードの定数にする（「エラーのルール」の 400）。
- 並び順は固定で、呼ぶ側では選べない。
  - 取引: 日付の新しい順。同じ日付は、あとから登録したほう（id の大きいほう）が先。
  - 分類ルール: 作った順（id の順。分類の一覧と同じ）。
  - 並び順が一意でないと、ページの間で同じ行が2回出たり抜けたりするため、最後は必ず id で並べる。

## 送るもの・返すもの

### 共通

- JSON の項目名は、先頭が小文字（`amount`、`merchant` など）。
- 種類（`type`）や入力元（`source`）のような決まった値は、小文字の名前（`expense`、`auto` など）で送る・返す。数字は受け付けない（400）。
- ユーザーの内部 ID は、送らせない・返さない。サーバーが、トークン（鍵のときは設定に書いたユーザー）から決める。
- 日付は日付だけで、`2026-10-17` の形（ISO 8601）。省略されたときの「今日」は、日本時間で決める。
- 一覧をページ分割するときは、次の形で返す。

```json
{
  "items": [],
  "page": 2,
  "pageSize": 50,
  "totalCount": 135
}
```

### 分類

| API | 送るもの（本文） | 返すもの（本文） |
| --- | --- | --- |
| `GET /categories` | なし | 分類の配列 `[{ "id": 1, "name": "食費" }]`（作った順） |
| `GET /categories/{id}` | なし | `{ "id": 2, "name": "日用品" }` |
| `POST /categories` | `{ "name": "交際費" }` | 201 で `{ "id": 8, "name": "交際費" }`。`Location` ヘッダーに `/categories/8` |
| `PUT /categories/{id}` | `{ "name": "生活用品" }` | なし（204） |
| `DELETE /categories/{id}` | なし | なし（204） |

- 名前は必須で、20文字まで。空白だけの名前は受け付けない（400）。名前の中に空白が入るのはよい。
- 名前の重複は、同じ人の分類の中で見る（409 `category.duplicate_name`）。
- 分類を消すと、その分類を指す分類ルールも一緒に消える。ルールがあるときに「本当に消しますか？」と確かめるのはクライアント。取引に使われている分類は消せない（409 `category.in_use`。このチェックは取引を作るときに足す）。
- 「未分類」は分類として持たない。どの分類ルールにも当たらない取引は、分類を空（null）にする。「未分類」と表示するのはクライアント。

### 取引

| 項目 | 名前 | 決まり |
| --- | --- | --- |
| id | `id` | サーバーが決める |
| 金額 | `amount` | 必須。1円以上、1,000万円未満の整数。いつもプラス |
| 店名 | `merchant` | 必須。50文字まで |
| 日付 | `date` | `2026-10-17` の形。省略したら日本時間の今日 |
| 種類 | `type` | `expense`（支出）か `income`（収入）。省略したら `expense` |
| 分類 | `categoryId` | 登録のときはサーバーが分類ルールで決める。どれにも当たらなければ空（null）＝未分類 |
| 入力元 | `source` | `auto`（自動。Apple Pay のショートカット）か `manual`（手入力）。登録のときにクライアントが送る（必須）。あとから変えられない |

| API | 送るもの（本文） | 返すもの（本文） |
| --- | --- | --- |
| `GET /transactions` | なし（条件は URL の `?` のあと） | ページ分割の形。`items` は取引の配列 |
| `GET /transactions/{id}` | なし | 取引1件 |
| `POST /transactions` | `{ "amount": 1200, "merchant": "ローソン", "date": "2026-10-17", "type": "expense", "source": "auto" }`（`date`・`type` は省略できる。`categoryId` は送らない） | 201 で取引1件。`Location` ヘッダーに `/transactions/{id}` |
| `PUT /transactions/{id}` | `{ "amount": 1200, "merchant": "ローソン", "date": "2026-10-17", "type": "expense", "categoryId": 1 }`（丸ごと置き換え。`categoryId` は空にもできる。`source` は送らない＝変えられない） | なし（204） |
| `DELETE /transactions/{id}` | なし | なし（204） |

#### 登録の送り直し（冪等キー）

- `POST /transactions` に `Idempotency-Key: （キー）` ヘッダーを付けられる。省略できる。付けるなら1〜64文字。送る側は支払いごとに UUID を1つ作り、送り直すときは同じキーを使う。
- 同じユーザー・同じキーの取引がもうあれば、新しく作らずにその取引を 201 で返す。1回目と同じ形で返すので、送る側は1回目か送り直しかを気にしなくてよい。
- 同じキーで、金額・店名・入力元のどれかが違えば 422 `transaction.idempotency_key_reused`。日付と種類は、省略すると今日・支出になり、日をまたいだ送り直しで変わりうるので比べない。
- キーは取引の列（`IdempotencyKey`）に保存し、ユーザーとキーの組に一意インデックスを付ける。同じキーのリクエストが同時に来ても、2件目は DB が断るので、先に登録された取引を返す。
- キーはユーザーごと。別のユーザーが同じキーを使っても、別の取引になる。
- キーに期限は無い。取引を消すとキーも一緒に消えるので、そのあとに同じキーで送ると新しく登録される。

取引1件の返し方:

```json
{
  "id": 15,
  "amount": 1200,
  "merchant": "ローソン",
  "date": "2026-10-17",
  "type": "expense",
  "categoryId": 1,
  "source": "auto"
}
```

- 支出か収入かは `type` で表し、金額はいつもプラス。＋・－の表示はクライアントに任せる。
- 分類は `categoryId` だけを返し、分類の名前は返さない。クライアントは分類の一覧（`GET /categories`）を別に取って手元に持ち、id から名前を引く（業務のマスターデータに近い考え方。返すデータを少なくするため）。分類の名前が変わったときは、クライアントが分類の一覧を取り直す。
- `source` は「どこから入ってきたか」の記録なので、`PUT` では変えられない。将来ほかの入力元（CSV の取り込みなど）が増えたら、値を足す。

### 分類ルール

| API | 送るもの（本文） | 返すもの（本文） |
| --- | --- | --- |
| `GET /category-rules` | なし | ページ分割の形。`items` は分類ルールの配列 |
| `GET /category-rules/{id}` | なし | `{ "id": 3, "keyword": "JR", "categoryId": 3 }` |
| `POST /category-rules` | `{ "keyword": "スタバ", "categoryId": 1 }` | 201 で1件。`Location` ヘッダーに `/category-rules/{id}` |
| `PUT /category-rules/{id}` | `{ "keyword": "JR東日本", "categoryId": 3 }`（丸ごと置き換え） | なし（204） |
| `DELETE /category-rules/{id}` | なし | なし（204） |

- キーワードは必須で、50文字まで（店名と同じ上限）。重複は同じ人のルールの中で見る（409 `category_rule.duplicate_keyword`）。
- 「当たる」とは、店名の中にキーワードの文字がそのまま入っていること。
- 1つの店名に2つ以上のルールが当たったときは、キーワードが長いほうを使う（より詳しく一致しているため）。長さも同じときは、先に作ったルールを使う。
- 取引の分類を手で直したときは、店名をそのままキーワードにしたルールを自動で作る。同じキーワードのルールがもうあるときは、新しく作らずに、そのルールの分類を直す。
- ルールを消しても、もう登録されている取引の分類は変わらない。

### 集計

- 送るものは URL の条件だけ（本文はなし）。返すものは次の形。

```json
{
  "from": "2026-10-01",
  "to": "2026-10-31",
  "totalExpense": 60000,
  "totalIncome": 250000,
  "balance": 190000,
  "byCategory": [
    { "categoryId": 1, "type": "expense", "total": 32000 },
    { "categoryId": 6, "type": "income", "total": 250000 },
    { "categoryId": null, "type": "expense", "total": 1200 }
  ]
}
```

- `from`・`to` には、実際に集計した期間を入れる（`month` で頼まれたときや、条件がなかったときも）。
- `balance` は収入 − 支出。マイナスになることもある。
- 分類別の合計は、取引と同じ「`type` と金額」の形にする。分類ごと・`type` ごとに1行で、0円の行は返さない。
- 分類は `categoryId` だけを返す（取引と同じ）。`null` は未分類。

### アカウントとログイン

| API | 送るもの（本文） | 返すもの（本文） |
| --- | --- | --- |
| `POST /accounts` | `{ "userName": "taro", "password": "（15文字以上）" }` | 201 で `{ "userName": "taro" }`。`Location` ヘッダーは付けない |
| `POST /tokens` | `{ "userName": "taro", "password": "（パスワード）" }` | 200 で `{ "accessToken": "...", "tokenType": "Bearer", "expiresIn": 3600 }` |

- ユーザー名は必須で、英数字と `-` `.` `_` `@` `+` だけ（Identity の既定と同じ）。256文字まで。メールアドレスは集めない。
- パスワードは15文字以上。大文字・数字・記号を混ぜる決まりは付けない（NIST SP 800-63B-4 の、パスワードだけでログインするときの考え方に合わせる）。
- アカウント作成で返すのはユーザー名だけ。内部 ID を返さず、1件を取る API も無いので、`Location` も付けない。
- アカウントと初期分類は1つのトランザクションでまとめて保存する。途中で失敗したら、どちらも保存されない。
- ログインの入力チェックは「空でないか」だけにする。長さや文字の決まりで 400 を返すと、どこが違うかのヒントになるため。
- ログインに失敗したときは、ユーザー名が無い・パスワードが違う・ロック中のどれでも、同じ文の 401 にする。どれなのかが外から分からないようにするため。
- 5回続けて失敗すると、5分ロックする（Identity の既定と同じ）。
- トークン（JWT）の中身は最小限（`sub`・`iss`・`aud`・`exp`・`iat`・`jti`）にする。JWT は誰でも中身を読めるため。
- トークンは RSA の秘密鍵で署名する（RS256）。確かめるときは、署名・発行者・対象者・期限をすべて見る。
- ログインは1分に5回、アカウント作成は1時間に3回まで（IP アドレスごと）。成功・失敗・入力エラーに関係なく、届いた回数で数える。超えたら 429 と、何秒後にまた試せるかを `Retry-After` ヘッダーで返す。ロックアウトは1人のアカウントしか守れず、たくさんのアカウントに少しずつ試す攻撃と大量の登録を止めるため。回数はアプリのメモリで数えるので、アプリが2つ以上動くとそれぞれ別に数える。

## エラーのルール

### 返し方

- エラーは Problem Details（RFC 9457）の形で返す。本文のないエラー（存在しない URL の 404 など）も、この形にそろえる。
- アプリが決めたエラー（ログインの 401・404・409・422）には、種類を見分けるために `code` にエラーコードを入れる。
- 入力チェックの 400 は `[ApiController]` の自動の検証が返し、`code` の代わりに `errors` に項目ごとの理由が入る。500（想定外）、存在しない URL の 404、トークンや鍵が無い・違うときの 401、鍵で呼べない API の 403、回数の超過の 429 には `code` を付けない。

```json
{
  "title": "取引に使われている分類は削除できません。",
  "status": 409,
  "code": "category.in_use"
}
```

### エラーコード

- 数字ではなく、意味の分かる文字列にする。
- 形は `リソース.何が起きたか`。小文字で、単語の区切りは `_`。
  - 例: `category.in_use`（分類が取引に使われている）、`category.duplicate_name`（同じ名前の分類がある）、`transaction.not_found`（取引が見つからない）
- C# の中では、エラーコードを1つのクラスの定数にまとめる。文字列をあちこちに直接書かない。

### ステータスコード

| コード | 使う場面 |
| --- | --- |
| 400 | 入力が正しくない（金額が範囲の外など）。`[ApiController]` の自動の検証に任せる。範囲や長さの値はコードの1か所（定数）にまとめ、検証の属性と DB の列の長さで同じ定数を使う |
| 404 | URL で指定したデータが見つからない。他人のデータを指定されたときも 404 にする |
| 409 | 今のデータの状態とぶつかる（分類が取引に使われている、名前が重複している） |
| 422 | 中身の形は正しいが、中身で指定したデータが存在しない（存在しない分類の id を指定した、など）。入力チェックの 400 と同じものを使い回さないため、分けた。取引の登録で、同じ冪等キーを内容の違う取引に使ったときも 422 |
| 401 | トークンも鍵も無い・どちらかが正しくない・トークンの期限が切れた。ログインでユーザー名かパスワードが違う（`token.invalid_credentials`） |
| 403 | 鍵で、鍵では呼べない API（取引の登録以外）を呼んだ |
| 429 | ログインかアカウント作成を、決めた回数より多く呼んだ。`Retry-After` ヘッダーに、また試せるまでの秒数を入れる |
| 500 | 想定外のエラー。中身（例外の詳細）は外に見せない |

### 処理の進め方

- エラーが分かった時点で処理をやめ、すぐにエラーを返す。
- DB への書き込み（`SaveChanges`）は、チェックがすべて終わってから最後に1回だけにする。途中まで書き込んだ状態を残さないため。

## 区分コード（DB に入る番号）

- 種類や入力元のような決まった値は、DB には番号で入れる（業務の区分コードと同じ考え）。
- 番号は enum（`TransactionType`・`TransactionSource`）に書いて固定する。あとから変えない。値を足すときは、新しい番号を付ける。
- API の JSON では名前（`expense` など）で送る・返し、番号は外に出さない（「送るもの・返すもの」の「共通」）。

| 項目 | 番号 | 意味 | JSON の値 |
| --- | --- | --- | --- |
| 種類（`type`） | 0 | 支出 | `expense` |
| 種類（`type`） | 1 | 収入 | `income` |
| 入力元（`source`） | 0 | 自動（Apple Pay のショートカット） | `auto` |
| 入力元（`source`） | 1 | 手入力 | `manual` |
