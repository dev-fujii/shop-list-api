# 設計

2026-10-17 時点。作りながら調整する。要件は `docs/要件定義.md`。

## API の一覧

- 1回のリクエストで1つの操作をする（REST）。まとめて送る API（バッチ API）は作らない。
- どの API も、ログインした人（ログインを作るまでは仮 ID の人）のデータだけを扱う。
- 送るもの・返すものの中身は、別の節で決める。
- URL の先頭に `api/` は付けない。API だけを返すサーバーで、画面などと分ける必要がないため。あとから付けると、iPhone のショートカットに書いた URL も直す必要があるので、変えない。

### 分類

| メソッド | URL | やること | 成功 | 主なエラー |
| --- | --- | --- | --- | --- |
| GET | `/categories` | 分類の一覧を取る | 200 | — |
| GET | `/categories/{id}` | 分類を1件取る | 200 | 404 `category.not_found` |
| POST | `/categories` | 分類を作る | 201 | 400（入力）、409 `category.duplicate_name` |
| PUT | `/categories/{id}` | 分類を直す（名前を変える） | 204 | 400（入力）、404 `category.not_found`、409 `category.duplicate_name` |
| DELETE | `/categories/{id}` | 分類を消す | 204 | 404 `category.not_found`、409 `category.in_use` |

### 取引

| メソッド | URL | やること | 成功 | 主なエラー |
| --- | --- | --- | --- | --- |
| GET | `/transactions` | 取引の一覧を取る。`?categoryId=3` で分類、`?from=2026-10-01&to=2026-10-31` で期間を絞れる（どれも省略できる）。ページ分割する | 200 | 400（条件の形が正しくない） |
| GET | `/transactions/{id}` | 取引を1件取る | 200 | 404 `transaction.not_found` |
| POST | `/transactions` | 取引を登録する。分類は分類ルールで自動で決める（自動の入力と手の入力で同じ API） | 201 | 400（入力） |
| PUT | `/transactions/{id}` | 取引を直す。分類を手で直したときは、次から同じ店がその分類になるようにする | 204 | 400（入力）、404 `transaction.not_found`、422 `category.not_found`（存在しない分類を指定） |
| DELETE | `/transactions/{id}` | 取引を消す（完全に消える） | 204 | 404 `transaction.not_found` |

### 分類ルール

| メソッド | URL | やること | 成功 | 主なエラー |
| --- | --- | --- | --- | --- |
| GET | `/category-rules` | 分類ルールの一覧を取る。ページ分割する | 200 | — |
| GET | `/category-rules/{id}` | 分類ルールを1件取る | 200 | 404 `category_rule.not_found` |
| POST | `/category-rules` | 分類ルールを作る（店名のキーワード → 分類） | 201 | 400（入力）、409 `category_rule.duplicate_keyword`、422 `category.not_found`（存在しない分類を指定） |
| PUT | `/category-rules/{id}` | 分類ルールを直す | 204 | 400（入力）、404 `category_rule.not_found`、409 `category_rule.duplicate_keyword`、422 `category.not_found`（存在しない分類を指定） |
| DELETE | `/category-rules/{id}` | 分類ルールを消す | 204 | 404 `category_rule.not_found` |

### 集計

| メソッド | URL | やること | 成功 | 主なエラー |
| --- | --- | --- | --- | --- |
| GET | `/summaries?month=2026-10` または `/summaries?from=2026-10-01&to=2026-10-31` | 月か期間の集計を取る（分類別の合計、支出の合計、収入の合計、収入 − 支出の残り）。条件は `month` か、`from` と `to` のどちらか一方で渡す | 200 | 400（条件が正しくない。`month` と `from`・`to` を両方送った、存在しない日付、`from` が `to` より後など） |

- 集計は1つのリソース（`/summaries`）として扱い、月か期間かは絞り込みの条件の違いにする（取引の一覧と同じ形）。
- 条件を何も送られなかったときにどうするかは、まだ決めていない。

### アカウント（2段目）

- アカウント作成・ログインの API は、2段目で Identity の使い方を決めてから書く。

### ページ分割

- 件数が増え続ける一覧（取引、分類ルール）は、何件かずつに分けて返す。分類（10〜20個）と集計（1件）は分けない。
- URL の例: `GET /transactions?page=2&pageSize=50`
- 何も指定されなかったときは1ページ 50件、指定できる上限は 100件。
- この値は `const` ではなく設定ファイル（`appsettings.json`）に置き、オプション パターンで読む。要件定義の「値は後から変えられるようにする」のため。

## 送るもの・返すもの

### 共通

- JSON の項目名は、先頭が小文字（`amount`、`merchant` など）。
- ユーザーの内部 ID は、送らせない・返さない。サーバーが、仮 ID（ログインを作ったあとはトークン）から決める。
- 日付は日付だけで、`2026-10-17` の形（ISO 8601）。省略されたときの「今日」は、日本時間で決める。
- 一覧をページ分割するときは、次の形で返す。

```json
{
  "items": [],
  "page": 2,
  "pageSize": 50,
  "totalCount": 135
}
```

### 分類

| API | 送るもの（本文） | 返すもの（本文） |
| --- | --- | --- |
| `GET /categories` | なし | 分類の配列 `[{ "id": 1, "name": "食費" }]`（作った順） |
| `GET /categories/{id}` | なし | `{ "id": 2, "name": "日用品" }` |
| `POST /categories` | `{ "name": "交際費" }` | 201 で `{ "id": 8, "name": "交際費" }`。`Location` ヘッダーに `/categories/8` |
| `PUT /categories/{id}` | `{ "name": "生活用品" }` | なし（204） |
| `DELETE /categories/{id}` | なし | なし（204） |

- 名前は必須で、20文字まで。空白だけの名前は受け付けない（400）。名前の中に空白が入るのはよい。
- 名前の重複は、同じ人の分類の中で見る（409 `category.duplicate_name`）。
- 「未分類」は分類として持たない。どの分類ルールにも当たらない取引は、分類を空（null）にする。「未分類」と表示するのはクライアント。

### 取引（決まっていること）

- 支出か収入かは、種類の項目で表す。値は `expense`（支出）か `income`（収入）。金額はいつもプラス。＋・－の表示はクライアントに任せる。

## エラーのルール

### 返し方

- エラーは Problem Details（RFC 9457）の形で返す。
- エラーの種類を見分けるために、`code` にエラーコードを入れる。

```json
{
  "title": "取引に使われている分類は削除できません。",
  "status": 409,
  "code": "category.in_use"
}
```

### エラーコード

- 数字ではなく、意味の分かる文字列にする。
- 形は `リソース.何が起きたか`。小文字で、単語の区切りは `_`。
  - 例: `category.in_use`（分類が取引に使われている）、`category.duplicate_name`（同じ名前の分類がある）、`transaction.not_found`（取引が見つからない）
- C# の中では、エラーコードを1つのクラスの定数にまとめる。文字列をあちこちに直接書かない。

### ステータスコード

| コード | 使う場面 |
| --- | --- |
| 400 | 入力が正しくない（金額が範囲の外など）。`[ApiController]` の自動の検証に任せる |
| 404 | URL で指定したデータが見つからない。他人のデータを指定されたときも 404 にする |
| 409 | 今のデータの状態とぶつかる（分類が取引に使われている、名前が重複している） |
| 422 | 中身の形は正しいが、中身で指定したデータが存在しない（存在しない分類の id を指定した、など）。入力チェックの 400 と同じものを使い回さないため、分けた |
| 401・403 | ログインしていない・権限がない（2段目） |
| 500 | 想定外のエラー。中身（例外の詳細）は外に見せない |

### 処理の進め方

- エラーが分かった時点で処理をやめ、すぐにエラーを返す。
- DB への書き込み（`SaveChanges`）は、チェックがすべて終わってから最後に1回だけにする。途中まで書き込んだ状態を残さないため。
