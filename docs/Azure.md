# Azure での構成

README の「Azure での構成」の詳しい内容です。

## 構成

```text
iPhone のショートカットなど
  → HTTPS
  → Azure Container Apps（入口で HTTPS を受ける。API が X-Api-Key の鍵か、ログインで受け取った JWT を確かめる）
  → Azure Database for PostgreSQL（Flexible Server。SSL で接続）

イメージ: GitHub Container Registry（GHCR）の公開イメージを、Container Apps が取ってくる
```

- **地域**: API と DB は、どちらも Japan East に置いています。離れていると、API が DB とやりとりするたびに遅くなるためです。
- **秘密の値**: DB の接続文字列・仮の鍵・JWT に署名する秘密鍵は、Container Apps の「シークレット」に入れ、環境変数（`ConnectionStrings__DefaultConnection`・`ApiKey__Key`・`Jwt__PrivateKey`）から参照しています。署名の秘密鍵は、手元とは別の値です。コード・イメージ・git には入れていません。
- **入口**: `https://` だけを受け付けます。`http://` で来たリクエストは `https://` に転送されます。鍵も JWT も無い・違うリクエストは 401 で止めます。鍵で呼べるのは取引の登録だけで、ほかを鍵で呼ぶと 403 です。
- **回数制限の送り元**: ログインとアカウント作成の回数は、送り元の IP アドレスごとに数えます。送り元は、入口が `X-Forwarded-For` の右端に足す値から読みます。アプリには入口を通らないと届かないので、送る側が `X-Forwarded-For` に別の IP を書いても、数え方は変わりません。
- **鍵が無いときは起動しない**: 仮の鍵や署名の秘密鍵の設定が無いと、起動の時点で止まるようにしています（`ValidateOnStart`）。署名の秘密鍵は、RSA の鍵として読めるかまで確かめます。入れ忘れたり、形の違う鍵を入れたりしたまま公開してしまうことを防ぐためです。
- **DB への接続**: パブリック アクセスで、「Azure サービスからのアクセス」と、マイグレーションを当てる PC の IP アドレスだけを通しています。Container Apps の従量課金プランは外へ出るときの IP アドレスが決まっていないため、無料で済ませるにはこの方法になります。その分、DB のパスワードは長いランダムな値にしています。
- **マイグレーション**: 移行バンドル（`dotnet ef migrations bundle` で作る実行ファイル）で当てています。公式ドキュメントが、公開する DB に流すやり方として勧めているためです。

## 無料に収めるための設定

| どこ | 設定 | 理由 |
| --- | --- | --- |
| PostgreSQL | Burstable B1ms・ストレージ 32GB | 12か月の無料枠（B1ms を月750時間・32GB）に収める |
| PostgreSQL | ストレージの自動拡張・高可用性・Geo 冗長はオフ | オンにすると、容量や予備のサーバーが増えて料金がかかる |
| Container Apps | 従量課金（Consumption）だけ・0.25 CPU・0.5 GiB | 毎月の無料枠（18万 vCPU秒・36万 GiB秒・200万リクエスト）を長く使える |
| Container Apps | レプリカは最小 0・最大 1 | だれも呼ばないときは0個になり、料金がかからない。急に呼ばれても1個までしか増えない |
| Container Apps | ログを保存しない | Log Analytics（ログの保存先）を作らない。今のログはログ ストリームで見られる |

公開している URL は、このリポジトリには載せていません。鍵の無いリクエストでもコンテナは起動するので、だれでも呼べる場所に書くと、無料枠を使い切るおそれがあるためです。

## Azure（Container Apps）に載せる流れ

### 新しい版を載せるとき

main に push すると、GitHub Actions がテストを実行し、全部通ったときだけイメージを作って GHCR に置きます（タグは commit の番号）。テストに失敗した commit のイメージは作られません。手元でイメージを作らないので、commit していない変更がイメージに入ることもありません。

Azure への反映は、次の順番で手で行います。

1. GitHub の「Actions」タブで、その commit の CI が `build-and-test` と `push-image` の両方とも成功したことを確かめます。
2. マイグレーションが増えた版なら、先に移行バンドルで Azure の DB に当てます。バンドルは、push した commit と同じ状態（`git status` に変更が無い）で作ります。
3. Container Apps で、イメージのタグをその commit の番号にした新しいリビジョンを作ります。
4. 公開側で、鍵も JWT も無いと 401、ログインで受け取った JWT なら 200 になることを確かめます。

マイグレーションを先に当てるのは、新しいコードが新しい列を使うためです。先にイメージを変えると、列が無い DB に新しいコードがつながり、エラーになります。反対に、新しい列が増えた DB に古いコードがつながっても、古いコードはその列を使わないので動きます（列が省略できる場合）。列を消す・名前を変えるマイグレーションは、古いコードが動かなくなるので、この順番では載せられません。そのときは、先にコードを列を使わない形にして載せ、次の版で列を消します。

GitHub Actions からは Azure に反映しません。DB のファイアウォールは Azure サービスと PC の IP アドレスだけを通しているので、Actions からは移行バンドルを当てられないためです。

### 最初に作ったとき

1. イメージを作り、GHCR に push します（タグは commit の番号にして、どのコードが動いているか分かるようにします）。
2. Azure に PostgreSQL（Flexible Server）を作り、移行バンドルで表を作ります。
3. Container Apps の環境とアプリを作り、GHCR のイメージを指定します。
4. シークレットに接続文字列・仮の鍵・署名の秘密鍵を入れ、環境変数から参照する新しいリビジョンを作ります。
5. 発行された URL で、鍵も JWT も無いと 401、ログインで受け取った JWT なら 200 になることを確かめます。

初期分類を Azure に入れる手順は、[動かし方.md](動かし方.md) の「初期分類の投入」にあります。

## Azure で確認したこと

commit `c7097b9`（ログインを入れた版）のイメージを反映し、次を確認しています（2026-11-03）。

- アカウントの作成（201）→ ログイン（200。JWT が返る）→ JWT で `GET /categories`（200。作ったアカウントの初期6分類）
- 鍵も JWT も無いと 401。鍵で `GET /categories` は 403、鍵で `POST /transactions` は通り、iPhone のショートカットから記録できること
- ログインで `X-Forwarded-For` に毎回違う IP を書いて送っても、6回目は 429 になること

それより前の版（commit `4bba03f`）で、次を確認しています。

- 初期分類の投入（初回6件追加・再実行0件）と、鍵付きの `GET /categories` で6つの名前がそれぞれ1件ずつあること
- 月指定の集計
- 取引の分類を手で変えるとルールができ、次の取引が自動で分類されること
- 分類ルールの更新が取得結果に反映され、削除後に取得すると404になること（2026-10-29）
