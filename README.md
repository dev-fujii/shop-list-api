# shop-list-api（家計の記録 API）

家計簿を毎回スマホで手で付けるのが面倒だったので、自動で記録できるようにした Web API です。
金額と店名だけで取引を登録でき、分類（食費・交通費など）は、自分で決めた分類ルールで自動で決まります。
月や期間を指定し、分類別の合計・収入・支出・収支も取得できます。
Apple Pay の決済時に、iPhone のショートカットから自動送信する動きは確認中です。

> 2026-10-29 時点：分類ルールの更新・削除、初期分類の投入、手動変更からのルール作成、集計まで実装し、Azure に反映しています。手元のビルドは警告・エラーともに0件、自動テスト33件（DBを使わない14件・DB統合19件）は成功しています。GitHub Actions の CI でも、PostgreSQL を起動して両方のテストが成功しています。
>
> Azure（Container Apps）では、初期分類の投入・再実行、月指定の集計、分類の変更からルールを作って次の取引を自動分類する動き、分類ルールの更新・削除を確認しています。iPhone のショートカットの手動実行による保存・自動分類も確認済みです。決済時の自動送信は確認中です。

## 作った理由

- 家計簿アプリで記録するには、毎回アプリを開いて、分類を選び、金額を入れる必要があります。これが面倒で続きませんでした。
- 入力を「金額と店名」だけにして、分類は自動で決まるようにすれば、記録の手間をほぼなくせると考えました。
- 家計簿アプリはすでにたくさんあります。この作品では、次の2点を自分で決められるようにしました。
  - 分類のしかた: 「店名にこの言葉が入っていたらこの分類」というルールを自分で作れます。取引の分類を手で直すと、店名をキーワードにした次回用のルールを追加・更新します。
  - 見せ方: 画面は持たない API だけの作りなので、記録したデータを好きな形で表示できます。

## 目指す記録の流れ

```text
Apple Pay で払う
  → iPhone のショートカット（「取引」のオートメーション）が金額と店名を送る
  → API が分類ルールで分類を決めて保存する

現金などのとき
  → 同じ API に、手で金額と店名を送る
```

- 自動の記録も手の記録も、同じ登録の API を使います。どちらから来たかは `source`（`auto` / `manual`）で残します。
- ショートカットそのものは、この作品の範囲外です。

## できること

手元の実装状況と、Azure で公開して確認した範囲を分けて示します。手元では `.http` ファイルで API を確認しています。Azure には commit `4bba03f` のイメージを反映し、初期分類・月指定の集計・分類変更から次回の自動分類を確認しています。

| 機能 | 手元 | Azure | 内容 |
| --- | --- | --- | --- |
| 取引 | 実装済み | 反映済み | 支出と収入を記録する。金額と店名だけで登録でき、日付を省くと今日になる。一覧・1件の取得・更新・削除 |
| 分類 | 実装済み | 反映済み | 分類の一覧・1件の取得・登録・更新・削除 |
| 自動分類 | 実装済み | 反映済み | 取引の登録時に、店名に含まれるキーワードから分類を決める。一致するルールが無ければ未分類（`null`）にする |
| 分類ルールの登録・取得 | 実装済み | 反映済み | 「店名のキーワード → 分類」を登録する。一覧（ページ分割）・1件を取得する。同じユーザーの同じキーワードは重複登録できない |
| 分類ルールの更新・削除 | 実装済み | 更新・削除を確認済み | 登録済みのルールを更新・削除する。過去の取引の分類は変わらない |
| 分類の初期データ | 実装済み | 動作確認済み | 専用コマンドで、仮ユーザーに「食費・日用品・交通費・趣味・固定費・給料」のうち不足する名前を追加する |
| 手動変更からのルール作成 | 実装済み | 新規作成と次回の自動分類を確認済み | 取引の分類を手で変えたとき、店名をキーワードにしたルールを作る。同じキーワードがあれば分類を更新する |
| 集計 | 実装済み | 月指定を確認済み | 月か期間を指定し、分類別・支出と収入の種類別の合計、支出・収入の合計と収支を返す |

画面（フロントエンド）は作りません。手元では `.http` ファイルなどから API を呼んで確かめます。

## Azure での構成

```text
iPhone のショートカットなど
  → HTTPS
  → Azure Container Apps（入口で HTTPS を受ける。API が X-Api-Key の鍵を確かめる）
  → Azure Database for PostgreSQL（Flexible Server。SSL で接続）

イメージ: GitHub Container Registry（GHCR）の公開イメージを、Container Apps が取ってくる
```

- **地域**: API と DB は、どちらも Japan East に置いています。離れていると、API が DB とやりとりするたびに遅くなるためです。
- **秘密の値**: DB の接続文字列と仮の鍵は、Container Apps の「シークレット」に入れ、環境変数（`ConnectionStrings__DefaultConnection`・`ApiKey__Key`）から参照しています。コード・イメージ・git には入れていません。
- **入口**: `https://` だけを受け付けます。`http://` で来たリクエストは `https://` に転送されます。鍵が無い・違うリクエストは 401 で止めます。
- **鍵が無いときは起動しない**: 鍵の設定が無いと、起動の時点で止まるようにしています（`ValidateOnStart`）。鍵を入れ忘れたまま公開してしまうことを防ぐためです。
- **DB への接続**: パブリック アクセスで、「Azure サービスからのアクセス」と、マイグレーションを当てる PC の IP アドレスだけを通しています。Container Apps の従量課金プランは外へ出るときの IP アドレスが決まっていないため、無料で済ませるにはこの方法になります。その分、DB のパスワードは長いランダムな値にしています。
- **マイグレーション**: 移行バンドル（`dotnet ef migrations bundle` で作る実行ファイル）で当てています。公式ドキュメントが、公開する DB に流すやり方として勧めているためです。

### 無料に収めるための設定

| どこ | 設定 | 理由 |
| --- | --- | --- |
| PostgreSQL | Burstable B1ms・ストレージ 32GB | 12か月の無料枠（B1ms を月750時間・32GB）に収める |
| PostgreSQL | ストレージの自動拡張・高可用性・Geo 冗長はオフ | オンにすると、容量や予備のサーバーが増えて料金がかかる |
| Container Apps | 従量課金（Consumption）だけ・0.25 CPU・0.5 GiB | 毎月の無料枠（18万 vCPU秒・36万 GiB秒・200万リクエスト）を長く使える |
| Container Apps | レプリカは最小 0・最大 1 | だれも呼ばないときは0個になり、料金がかからない。急に呼ばれても1個までしか増えない |
| Container Apps | ログを保存しない | Log Analytics（ログの保存先）を作らない。今のログはログ ストリームで見られる |

公開している URL は、この README には載せていません。鍵の無いリクエストでもコンテナは起動するので、だれでも呼べる場所に書くと、無料枠を使い切るおそれがあるためです。

## 設計で決めたこと

細かい内容は [docs/設計.md](docs/設計.md) にあります。ここでは主なものだけ書きます。

- **REST で、1回のリクエストで1つの操作をする。** まとめて送る API は作りません。今はまとめて送る場面がなく、作る手間に見合わないためです。
- **分類の決め方。** 店名の中にキーワードがそのまま入っていれば当たりとし、大文字・小文字は区別します。2つ以上のルールが当たったら、キーワードが長いほう（より詳しく一致したほう）を使います。同じ長さなら、ルールの id が小さいほうを優先します。
- **手動変更からのルール作成。** 分類が以前と違い、新しい分類が空（`null`）ではないときに、更新後の店名をそのままキーワードにします。同じキーワードのルールがあれば増やさずに分類を更新します。金額・日付・店名だけの変更や、未分類への変更ではルールを変えません。取引とルールをまとめて保存し、片方だけが更新された状態を残さないようにしています。
- **集計の期間。** 月か、開始日と終了日を指定し、両端の日も含めます。条件を省略したときは、日本時間の今月を含む3か月です。月数は設定ファイルの `Summary:DefaultMonthCount` で変えられます。未分類も含めて集計し、取引が無い場合は合計0・分類別の一覧は空になります。
- **未分類は分類として持たない。** どのルールにも当たらない取引は分類を空（`null`）にして、「未分類」と表示するのはクライアントに任せます。こうすると、「消せない未分類」という特別な分類を守る処理がいらなくなります。
- **金額は円の整数で、いつもプラス。** 支出か収入かは `type`（`expense` / `income`）で表します。
- **エラーは Problem Details（RFC 9457）の形にそろえる。** アプリが決めたエラー（見つからない・ぶつかる など）には、種類を見分けるために `category.in_use` のような意味の分かる文字列のコードを付けます。入力の誤り（400）は、項目ごとの理由を `errors` で返します。
- **値の置き場所を2つに分ける。** 金額の範囲や文字数など DB の形に関わる値はコードの定数に、1ページの件数など運用しながら変えたい値は設定ファイル（`appsettings.json`）に置きます。
- **一覧の並び順は固定。** ページ分割したときに同じ行が2回出たり抜けたりしないように、最後は必ず id で並べます。

### API の一覧

| リソース | URL | 状態 | 操作 |
| --- | --- | --- | --- |
| 分類 | `/categories` | Azure反映済み | 一覧・1件・登録・更新・削除 |
| 取引 | `/transactions` | Azure反映済み | 一覧（分類・期間で絞れる。ページ分割）・1件・登録・更新・削除。分類変更からのルール作成・次回の自動分類もAzureで確認済み |
| 分類ルール | `/category-rules` | Azure反映済み | 一覧（ページ分割）・1件・登録 |

| 集計 | `/summaries` | Azure反映済み・月指定を確認済み | `?month=2026-10` か `?from=...&to=...` で月か期間の集計を返す |

送るもの・返すもの・エラーの一覧は [docs/設計.md](docs/設計.md) を見てください。

## 動かし方

### 手元（Docker Compose）

Docker Desktop を起動してから、リポジトリの一番上のフォルダーで実行します。

1. `.env.example` をコピーして `.env` を作り、パスワードと仮の鍵を書き換えます（`.env` は git に入れません）。

   ```powershell
   Copy-Item .env.example .env
   ```

2. DB のデータを置くボリュームを作ります（初めてのときだけ）。

   ```powershell
   docker volume create kakeibo-db-data
   ```

3. API と DB を起動します。

   ```powershell
   docker compose up --build -d
   ```

4. マイグレーションを適用し、表を作成・更新します。初回と、新しいマイグレーションが追加されたときに実行します。`ShopListApi/ShopListApi` のフォルダーで、`.env` に書いた値に合わせて実行します。

   ```powershell
   dotnet ef database update --connection "Host=localhost;Port=5433;Database=kakeibo;Username=postgres;Password=（.env の POSTGRES_PASSWORD）"
   ```

5. 呼んで確かめます。鍵が無ければ 401、`.env` の `API_KEY` を付ければ 200 が返ります。

   ```powershell
   curl.exe -i http://localhost:8080/categories
   curl.exe -i -H "X-Api-Key: （.env の API_KEY）" http://localhost:8080/categories
   ```

   ポートは `.env` の `API_PORT`（書かなければ 8080）です。

### 初期分類の投入

`--initialize-categories` を指定して起動すると、現在の仮ユーザーに初期分類を追加し、Web サーバーを起動せず終了します。先にマイグレーションを適用し、DB の表を作っておきます。

- 対象は「食費・日用品・交通費・趣味・固定費・給料」の6つです。
- 自分が同じ名前の分類を持っていれば再利用し、不足する名前だけを追加します。分類の ID は DB が決めます。
- 通常の API 起動時には実行しません。分類を削除・改名しても、起動するたびに元の名前が復活することはありません。
- このコマンドを明示的に再実行すると、その時点で不足する初期名を補います。削除した名前や改名前の名前も、再実行では追加対象になります。
- 現在は全リクエストで同じ仮ユーザーを使います。アカウント作成時に利用者ごとの初期分類を用意する処理は、認証の導入時に接続します。

#### 手元（Docker Compose）

上の「手元（Docker Compose）」の手順で、現在のコードから API のイメージをビルドし、DB の起動とマイグレーションの適用を済ませます。リポジトリの一番上のフォルダーで実行します。

```powershell
docker compose run --rm --no-deps api --initialize-categories
```

`api` サービスと同じイメージ・接続設定で、初期化だけを行う一時的なコンテナを起動します。DB は起動済みのものを使い、処理が終わると一時的なコンテナを削除します。既存の API コンテナの起動コマンドは変更しません。

ログの `初期分類をX件追加しました。` を確認します。何も削除・改名していない状態でもう一度実行し、追加0件になることを確かめます。通常の API に `GET /categories` を送り、6つの名前がそれぞれ1件ずつあることも確認します。

Visual Studio や `dotnet run` で動かす場合は、API プロジェクトのユーザーシークレットに、通常のローカル実行と同じ `ConnectionStrings:DefaultConnection` を設定しておきます。DB を起動したうえで、リポジトリの一番上から次を実行できます。

```powershell
dotnet run --project ShopListApi/ShopListApi/ShopListApi.csproj -- --initialize-categories
```

`.slnx` がある `ShopListApi` フォルダーから実行する場合は、`--project ShopListApi/ShopListApi.csproj` にします。DB の接続先は手元の PostgreSQL（既存の設定では `localhost:5433`）です。API キーや接続文字列の実値は、README や `.http` ファイルには書きません。

#### Azure（Container Apps）

以下は、このアプリの初期分類を Azure に投入した手順です。commit `4bba03f` のイメージで、初回6件追加・再実行0件と、鍵付きの `GET /categories` で6つの名前がそれぞれ1件ずつあることを確認しています。

1. 初期化コマンドを含む現在のコードでイメージを作り、GHCR に push して Container Apps の新しいリビジョンに反映します。DB の表は、先に移行バンドルで作成・更新しておきます。
2. 新しいリビジョンに、Azure の DB を指す `ConnectionStrings__DefaultConnection` がシークレット参照で設定されていることを確認します。API 用の `ApiKey__Key` も、通常どおり設定します。
3. アプリがスケール0で停止していれば、鍵付きの API リクエストを送って起動し、実行中のレプリカができるまで待ちます。
4. Azure portal で対象の Container App を開き、「監視」→「コンソール」を選びます。接続先に新しいリビジョン・実行中レプリカ・API のコンテナを選び、アクセス方法に `sh`（`/bin/sh`）を指定します。
5. API 本体のコンソールで、次を実行します。

   ```sh
   cd /App
   dotnet ShopListApi.dll --initialize-categories
   ```

6. コンソールに `初期分類をX件追加しました。` と表示されることを確認します。何も削除・改名せずに同じコマンドを再実行し、追加0件になることと、公開側の `GET /categories` に6つの名前がそれぞれ1件ずつあることを確認します。

`/App` と `ShopListApi.dll` は、このリポジトリの Dockerfile の配置に合わせています。このアプリでは、コンテナに設定した DB 接続情報で投入できることを確認しています。接続文字列をコンソールに直接入力する必要はありません。

スケール0の後に再び起動すると、レプリカが前回と変わることがあります。コンソールに再接続するときは、接続先の一覧から現在実行中のレプリカを選び直します。

初期化の引数はコンソール内の単発コマンドだけに付けます。アプリ本体の通常の起動は、Dockerfile の `dotnet ShopListApi.dll` のままにします。初期化用の引数を通常の起動設定に付けると、Web サーバーが起動せず終了するためです。

接続先は実行中の API コンテナの「コンソール」です。「デバッグコンソール」は別のコンテナを使う機能なので、ここでは使いません。接続方法は [Microsoft Learn のコンテナーコンソールの説明](https://learn.microsoft.com/ja-jp/azure/container-apps/container-console)、レプリカが存在しない場合については [az containerapp exec の説明](https://learn.microsoft.com/ja-jp/cli/azure/containerapp?view=azure-cli-latest#az-containerapp-exec)を参照してください。

### 自動テスト

リポジトリの一番上のフォルダーで実行します。DB を使わない14件だけを動かす場合は、次のように指定します。

```powershell
dotnet test ShopListApi/ShopListApi.Tests/ShopListApi.Tests.csproj --filter "TestCategory!=Integration"
```

DB を使わない自動テストは14件です。分類の判定4件と、集計の期間・条件10件を確認します。

分類の判定（4件）:

- 長いキーワードを優先する
- キーワードが同じ長さなら、ルールの id が小さいほうを優先する
- 一致するルールが無い場合と、ルールが空の場合は `null` を返す
- 大文字・小文字を区別して一致を判定する

集計の期間・条件（10件。複数の入力値を使うテストを含む）:

- 月の1日～末日になること（うるう年、平年、30日の月、9999年12月）
- 年をまたぐ既定の期間と、設定した月数（1か月・6か月）
- 開始日と終了日が同じ1日だけの期間
- 不正な年月、月と期間の併用、不完全な期間、日付の逆転の拒否
- 条件なし、月指定、開始日と終了日の指定を受け付けること

#### PostgreSQLを使う統合テスト（19件）

既存のサービス・`AppDbContext`・実際の PostgreSQL 17 をつなぎ、保存結果を別の `DbContext` から読み直します。HTTP のルーティング・認証・入力チェックは、この統合テストの対象には含めていません。

| 対象 | 件数 | 確認すること |
| --- | --- | --- |
| 手動変更からのルール作成 | 12 | 新規作成と次回の自動分類、既存ルールの更新、更新後の店名の利用、分類不変・未分類への変更では学習しないこと、他人の分類・取引・ルールとの分離、競合時の再試行、保存失敗時の巻き戻し |
| 保存直前に消された場合 | 2 | 取引の作成中に分類が消えても未分類で保存すること、更新中に取引が消えたら404にしてルールも残さないこと |
| 初期分類 | 2 | 6件追加と再実行0件、不足分だけの追加、既存IDの維持と所有者ごとの分離 |
| 集計 | 3 | 月・期間指定と両端の日、未分類と支出・収入別の合計、期間外・他人の取引の除外、空の結果、intを超える合計 |

Docker Desktop を起動し、[compose.tests.yaml](compose.tests.yaml) でテスト専用の DB サーバーを起動します。通常の Compose とプロジェクト名・ポート・保存領域を分け、既存の DB ボリュームと `.env` は使いません。

```powershell
docker compose -f compose.tests.yaml up -d --wait
$env:SHOPLIST_TEST_POSTGRES = "Host=127.0.0.1;Port=55432;Database=shoplist_tests;Username=shoplist_test;Password=shoplist_test_password"
dotnet test ShopListApi/ShopListApi.Tests/ShopListApi.Tests.csproj --filter "TestCategory=Integration"
```

テスト用 DB のポートは `127.0.0.1` だけに公開しているため、手元では `Host=localhost` ではなく `127.0.0.1` を指定します。Windows で `localhost` にすると先に IPv6（`::1`）へ接続しようとして待ち時間が生じ、2件で約34秒かかったり接続がタイムアウトしたりしました（`127.0.0.1` では全件約1秒）。CI は Linux 上のサービスコンテナなので `localhost` のままにしています。

接続先はローカルの `shoplist_tests` に限定しています。各テストはそのサーバー内にランダムな名前の専用 DB を作り、アプリと同じマイグレーションを適用して、終了時に削除します。上のユーザー・パスワードは使い捨てのテスト専用です。Azure や通常の開発用 DB の接続情報は設定しません。

競合のテストは、保存直前に別の接続からルールを登録・削除し、PostgreSQL の一意制約や更新件数による競合を再現します。分類を保存前に削除するテストでは、外部キー違反で失敗したときに取引とルールが片方だけ更新されないことも確認します。取引の作成では、分類が消えても支払いの記録を失わないよう、未分類で保存し直すことを確認します。

`SHOPLIST_TEST_POSTGRES` が未設定・不正な場合や、DB に接続できない場合は、統合テストを失敗させます。DB を用意せずに成功扱いでスキップすることはありません。

DB が起動し、接続設定がある状態で `--filter` を省くと、計33件を実行します。終了後は、テスト専用のコンテナを停止・削除できます。

```powershell
docker compose -f compose.tests.yaml down
Remove-Item Env:SHOPLIST_TEST_POSTGRES
```

#### HTTPを通した手動確認

HTTP API と DB を通した確認は、[ShopListApi.http](ShopListApi/ShopListApi/ShopListApi.http) と [家計仕上げ.http](ShopListApi/ShopListApi/家計仕上げ.http) から手動で行います。前者の101～125は分類ルールの更新・削除、後者の1～39は初期分類の確認・手動変更からのルール作成・集計の確認です。Visual Studio の HTTP エディターでは `dev` 環境を選びます。

両ファイルの `ShopListApi_HostAddress` は、起動方法に合わせます。既定の `http://localhost:5247` はローカルの開発用で、Docker Compose では `http://localhost:8080`（`API_PORT` を変えた場合はそのポート）にします。

### GitHub Actions（CI）

[.github/workflows/ci.yml](.github/workflows/ci.yml) に、次の処理を順番に実行する設定を追加しています。

1. テスト専用の PostgreSQL 17 をサービスコンテナで起動し、接続できるまで待つ
2. .NET 10 SDK を準備し、パッケージを復元する
3. ソリューション全体を Release 構成でビルドする
4. DB を使わないテスト14件を実行する
5. DB 統合テスト19件を実行する

main への push と main 向けのプルリクエストで自動実行します。GitHub の「Actions」タブから「CI」を選び、手動実行することもできます。
CI 内の PostgreSQL は `localhost:5432` で接続し、専用の `SHOPLIST_TEST_POSTGRES` を統合テストのステップに渡します。アプリや Azure の DB 接続情報・API キー・GitHub Secrets の追加は不要です。

GitHub 上の初回 CI は、分類の判定テスト4件の版で 2026-10-28 に成功しました（[実行結果](https://github.com/dev-fujii/shop-list-api/actions/runs/40533822473)）。集計のテストを加えた計14件の版（commit `4bba03f`）も、push 後の CI 成功を確認しています。DB 統合テストを加えた計33件の版（commit `85d2cfc`）は、2026-10-29 に DB を使わない14件・DB 統合19件とも成功しました（[実行結果](https://github.com/dev-fujii/shop-list-api/actions/runs/40887399455)）。各実行の結果は「Actions」タブで開き、ビルドと両方のテストの成功を確かめます。

### Azure（Container Apps）に載せる流れ

1. イメージを作り、GHCR に push します（タグは commit の番号にして、どのコードが動いているか分かるようにします）。
2. Azure に PostgreSQL（Flexible Server）を作り、移行バンドルで表を作ります。
3. Container Apps の環境とアプリを作り、GHCR のイメージを指定します。
4. シークレットに接続文字列と仮の鍵を入れ、環境変数から参照する新しいリビジョンを作ります。
5. 発行された URL で、鍵なしは 401、鍵ありは 200 になることを確かめます。
